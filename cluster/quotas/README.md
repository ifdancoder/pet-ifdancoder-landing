# Деление ресурсов между проектами

Это не про `landing` конкретно — это общая политика для всего кластера на сервере `nsk-1-vm-y6pb`, который теперь делят несколько независимых проектов (`landing`, `kip`, и те, что появятся дальше). Живёт в этом репозитории просто потому, что другого инфраструктурного репо пока нет — переносить сюда специфику каждого проекта не нужно, этот каталог про сам кластер.

## Зачем

У ноды 3.8 ГБ RAM. Без `ResourceQuota` любой namespace может запросить сколько угодно, и планировщик Kubernetes это разрешит — ровно так `kip` (Elasticsearch + Celery + RabbitMQ + Grafana + Prometheus + Tempo + Ollama + MinIO + свой Postgres, без единого заданного `resources.requests`) съел почти всю память ноды, и `landing` с ingress-nginx начали падать не из-за своих проблем, а потому что на хосте физически не осталось ресурсов.

`ResourceQuota` — жёсткий потолок на сумму `requests`/`limits` всех подов в namespace. `LimitRange` — дефолтные `requests`/`limits` для контейнеров, которые сами ничего не указали (без него `ResourceQuota` на namespace, где поды не объявляют ресурсы, либо не даст их создать вообще, либо квота окажется бессмысленной).

## Арифметика текущего разделения (`landing-quota.yaml` + `kip-quota.yaml`)

|                                                      | requests.memory                | limits.memory |
| ---------------------------------------------------- | ------------------------------ | ------------- |
| landing                                              | 768Mi                          | 1Gi           |
| kip                                                  | 2Gi                            | 2.5Gi         |
| системное (kube-system, ingress-nginx, cert-manager) | без квоты, по факту ~400-500Mi | —             |
| **Итого из 3.8Gi**                                   | **~3.3Gi**                     | —             |

Это уже впритык, с запасом буквально на один некрупный новый проект, не больше. И это квота для `kip` **на уровне того, что он и так сейчас потребляет по факту** (ElasticSearch ~840Mi + Celery ~670Mi + Grafana/RabbitMQ/Prometheus/Tempo ~350Mi, плюс Ollama и MinIO, которые в снимке `ps aux` не попали, но тоже не бесплатны) — то есть квота не "подрежет" `kip` искусственно, она просто зафиксирует его текущий, уже большой аппетит.

**Вывод:** квоты останавливают ситуацию "один проект молча съедает всё", но они не создают память из воздуха. Если `kip` останется таким же тяжёлым и добавится ещё 2-3 проекта — либо `kip` придётся сознательно ужимать (отключать Ollama/Elasticsearch когда не нужны, урезать heap), либо снова расти по RAM, либо выносить тяжёлые проекты на отдельную ноду/VPS. Эти квоты только показывают момент, когда новый проект уже не влезет (`ResourceQuota exceeded` при деплое — явная ошибка, а не тихая деградация соседей), а не решают нехватку сами по себе.

## Применение (один раз на namespace, под админским kubeconfig)

```bash
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
kubectl apply -f cluster/quotas/landing-quota.yaml
kubectl apply -f cluster/quotas/kip-quota.yaml
```

Для каждого следующего проекта — копия `landing-quota.yaml` с новым именем/namespace и своими цифрами (вычти из оставшегося остатка, не из общих 3.8Gi).

## Важное про `kip`

`LimitRange` подставляет дефолтные `requests`/`limits` только **контейнерам, у которых они не заданы**, и только при создании/пересоздании пода — на уже работающие поды задним числом не действует. Для компонентов с сильно разным и предсказуемым аппетитом (особенно Elasticsearch — он сам слушает `-Xms512m -Xmx512m`) надёжнее явно прописать `resources` в манифестах самого `kip`, а не полагаться на общий дефолт namespace — иначе при пересоздании пода он может упереться в заниженный дефолтный лимит и не подняться.
